►► Знакомая ситуация

Общая тетрадь без черновика

Все пишут одновременно, сразу ручкой. Ошибся — не исправить. Написал поверх чужого — чужое пропало

►► Зачем это в проекте

Что даёт процедура

  • незаконченное не попадает в основную версию
  • код читает человек до публикации
  • у изменения появляется документ: зачем оно
  • третий элемент критерия «Культура работы с Git»

►► Понятие 1

Pull Request — заявка, а не кнопка

Семь шагов: ветка → коммиты → отправка на сервер → описание → ревью → доработка → принятие

git push -u origin feature/sort-price

►► Что пишут в PR

Описание из трёх блоков

  • Что сделано — по пункту на файл
  • Как проверить — пронумерованные шаги
  • Что осталось — честно, чего здесь нет
Заголовок: Сортировка меню по цене

## Что сделано
- в script.js добавлена функция sortByPrice
- в index.html добавлена кнопка «Сначала дешёвые»

## Как проверить

## Что осталось
- обратная сортировка — отдельной задачей

Update script.js + пустое описание

Ревьюер не знает: что изменилось · как проверить · законченная ли работа. Пойдёт читать диф с нуля и напишет «выглядит нормально»

►► Понятие 2

Code Review: пять пунктов

  • понятны ли имена
  • нет ли мусора и console.log
  • работает ли на 320 px
  • обработаны ли пустые данные
  • может ли автор объяснить

►► Ищем вместе

Найдите здесь три нарушения

Читаем по пунктам: сначала все имена, потом весь мусор, потом нештатные ситуации

const b = document.querySelector(".sort-btn");
// const old = document.querySelector(".button-old");
b.addEventListener("click", function () {
  const arr = PIES.sort((x, y) => x.price - y.price);
  document.querySelector(".list").innerHTML = "";
  console.log("отсортировал");
});

Обсуждаем код, а не человека

«На 320 px кнопка выезжает за край» — работает. «Ты не подумал о телефоне» — не работает

►► Понятие 3

Merge — и конфликт

Конфликт возникает при одном условии: одну и ту же строку изменили в двух ветках по-разному. Git не угадывает — он выкладывает оба варианта

<<<<<<< HEAD
  { id: "kalitka", name: "Калитка с картошкой", price: 50, kind: "солёное" },
=======
  { id: "kalitka", name: "Калитка с картошкой", price: 55, kind: "солёное" },
>>>>>>> feature/price-update

►► Так нельзя

Удалить весь спорный кусок

►► Так нельзя

Служебные строки исчезли, страница открылась, ошибок нет. И калитка пропала из меню совсем — заметят через занятие

►► Вопрос

Вы правите строку 10, напарник — строку 80. Конфликт?

Один файл. Разные строки. Что скажет Git?

Обсуждаем вслух, ответ не показываем сразу

Сегодня ваш код читает одноклассник

Не педагог. Одноклассник. И вы читаете его код

►► ИИ в работе

Модель — первый ревьюер, человек — второй

Модель ловит механическое: имена, console.log, необработанный пустой массив. Пункты 3 и 5 остаются человеку: она не открывала страницу и не спросит вас про строку

Контекст: я школьник, делаю учебный сайт школьного буфета на чистых
HTML, CSS и JavaScript, без фреймворков и без сборщиков. Код ниже —
изменения, которые я собираюсь отправить в Pull Request.

Задача: проведи Code Review этого фрагмента по чек-листу из пяти пунктов:
1) понятны ли имена переменных и функций;
2) нет ли закомментированного кода, отладочных console.log и alert;
3) есть ли риски на узком экране (ширина 320 px) — по коду, без запуска;
4) обработаны ли нештатные ситуации: пустой массив, пустой ввод,
   отсутствие элемента на странице;
5) есть ли места, которые трудно объяснить словами.

Код:
<<< сюда вставить свой фрагмент >>>

Ограничения:
- не переписывай код целиком, только укажи на места;
- каждое замечание — по формуле: строка или фрагмент + что не так +
  почему это плохо;
- не предлагай подключать библиотеки, фреймворки и сборщики;
- не хвали код, хвалить не нужно;
- если по какому-то пункту замечаний нет — так и напиши.

Формат ответа: список замечаний, сгруппированный по пяти пунктам
чек-листа. Не больше восьми замечаний всего.

Критерии проверки: каждое замечание я должен уметь исполнить, не задавая
уточняющих вопросов.

Проверить руками: замечание указывает на существующее место · нет библиотек и фреймворков · пункт 3 проверен тобой в браузере на 320 px · пункт 5 — объясни вслух · страница после правок работает

Правило курса: сдаётся только то, что ты можешь объяснить

Глоссарий занятия 14

Pull Request (PR)
Заявка на перенос изменений из своей ветки в основную. Состоит из семи шагов: ветка, коммиты, отправка, описание, ревью, доработка, принятие.
Code Review
Чтение чужого кода перед принятием по конкретному чек-листу. На курсе чек-лист из пяти пунктов: имена, мусор, узкий экран, нештатные ситуации, объяснимость.
Merge (слияние)
Перенос коммитов одной ветки в другую. Техническое действие; Pull Request — процедура вокруг него.
Коммит слияния
Коммит, который создаётся при принятии Pull Request. Содержит номер PR, по которому потом находят обсуждение и замечания.
Конфликт слияния
Ситуация, когда одну и ту же строку изменили в двух ветках по-разному. Git не выбирает сам: он выкладывает оба варианта в файл и ждёт решения человека.
Служебные строки конфликта
<<<<<<< HEAD, ======= и >>>>>>> имя-ветки. Отмечают границы двух вариантов. После разрешения конфликта в файле не должно остаться ни одной из них.
Диф
Построчное сравнение до и после. Зелёные строки со знаком + добавлены, красные со знаком − удалены. Ревьюер читает диф, а не весь файл.
Ветка-фича
Ветка под одну задачу, живущая от начала работы до принятия PR. После слияния удаляется. Именуется feature/имя-задачи или fix/что-чинится, латиницей в нижнем регистре.
Замечание по существу
Комментарий к конкретной строке по формуле «место + что не так + почему». Отличается от оценочной реплики тем, что его можно исполнить, не задавая вопросов.
Первый ревьюер
Роль ИИ на курсе: модель ищет механические огрехи (имена, отладочные строки, необработанный пустой массив) до того, как код прочитает человек. Проверку на узком экране и объяснимость кода она закрыть не может.
