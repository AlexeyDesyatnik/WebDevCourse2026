### Что подготовить до занятия

- **Пройти весь путь накануне на тестовом репозитории:** ветка → PR → комментарий к строке → доработка → конфликт → разрешение → слияние. Особенно проверить, что комментарии к строкам дифа на вашей платформе доступны ученическим учётным записям.
- **Проверить возможность добавлять участников в репозиторий** на доступной платформе. Если её нет — заранее подготовить запасной вариант из подтемы 5.7 и не выяснять это в 38-ю минуту.
- **Подготовить две ветки для демонстрации конфликта:** в `main` цена калитки 50, в `feature/price-update` — 55. Конфликт должен возникнуть с первого нажатия «Merge», без импровизации на проекторе.
- **Подготовить фрагмент кода с пятью нарушениями** (раздел 11, часть 2) — вывести на слайд 8 и раздать на бумаге.
- **Раздаточные карточки:** список задач для веток, шаблон описания PR в три блока, чек-лист ревьюера из пяти пунктов. По одной на ученика.
- **Составить пары заранее**, а не на занятии. Учесть темп: сильного с сильным — они успеют по два PR; отстающего — с тем, кто объяснит.
- **Резервный вариант при недоступности платформы:** слияние делается локально командой `git merge feature/...`, ревью — по бумажному чек-листу с записью замечаний в тетрадь, конфликт провоцируется теми же двумя ветками. Контрольная точка в этом случае фиксируется педагогом по выводу `git log --oneline --graph`.

### Где группа обычно застревает

1. **Ветка не отправлена, кнопки PR нет.** Признак: «у меня нет кнопки». Готовое действие: не подсказывать команду сразу, а попросить открыть список веток на сервере — ученик сам увидит, что там одна `main`. После этого `git push -u origin имя-ветки` запоминается навсегда. Разбирать сразу на контроле 55-й минуты.
2. **Доработка уехала в `main` вместо ветки.** Признак: PR не обновляется, а в `main` появились новые коммиты. Готовое действие: научить проверять первую строку `git status` перед каждым коммитом. Если изменения уже в `main` — не паниковать: их можно перенести, но на занятии проще откатить `git revert` и повторить в ветке.
3. **Пара приняла PR друг у друга за полторы минуты, не читая.** Признак: ноль комментариев в PR. Готовое действие: переоткрыть PR (кнопка «Reopen») и провести ревью вместе с педагогом вслух, по одному пункту чек-листа. Одного такого разбора на группу обычно достаточно: остальные пары начинают читать всерьёз.

## 15. Домашнее задание и связь с проектом

### Домашнее задание (20–30 минут)

1. Открой закрытый сегодня Pull Request и перечитай его целиком: описание, диф, замечания, свои ответы. Выпиши в тетрадь **одно замечание напарника, которое ты сначала считал придиркой**, и рядом — было оно по делу или нет, с аргументом в одну строку.
2. Проведи ревью **своего же** старого кода. Возьми `script.js` из репозитория и пройди по пяти пунктам чек-листа. Выпиши все найденные нарушения списком: строка + пункт + что не так. Меньше трёх — значит, смотрел невнимательно, пройди ещё раз по пунктам подряд.
3. Исправь любые два из найденных нарушений. Каждое — в отдельной ветке `fix/<что-чинишь>` и отдельным коммитом с осмысленным сообщением. Отправь обе ветки на сервер.
4. Создай Pull Request для одной из двух веток и заполни описание по трём блокам — в блоке «Как проверить» обязательно должен быть пункт про ширину 320 px.

Сдаётся ссылкой на PR. Педагог смотрит описание и качество замечаний из пункта 2 — код открывать не потребуется.

**Контрольная точка программы:** «принятый Pull Request» (модуль 5). Проверяется по списку веток и закрытому PR со статусом «слит». Ученик, у которого PR закрыт кнопкой «Close» без слияния, контрольную точку не прошёл — это надо проверить лично у каждого до конца занятия.
